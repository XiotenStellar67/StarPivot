## 1. 它是什么，边界在哪

星枢在设备上以 `uid=2000(shell)` 执行命令，并把结果通过 `http://127.0.0.1:<port>/v1/*` 暴露给同设备的其它应用。

**能做的**：截屏、点击/滑动/按键注入、列进程、杀进程、列目录、读文件、写文件、删文件、列应用、启动应用、卸载应用、以及任意 shell 命令。

**不能做的**（设计上就没有）：

- 不提供「安装 HAP」接口（签名与安装刻意留给用户自己）
- 不跨设备、不监听外部网卡，只绑 `127.0.0.1`
- 不提供长期后台守护：Android 侧那种 "binder 常驻" 没有对应物，权限来源是设备的 `hdcd` 守护进程
- 设备锁屏时无法解锁（系统限制，不是接口缺项）

**权限等级**：`uid=2000(shell)`。比普通应用高，但**不是 root**。它读不到部分 `param`（例如序列号，`param get const.product.sn` 会返回 `errNum 106`），也改不了系统分区。

## 2. 通信模型：不是标准 HTTP 服务器

这一点最容易让调用方写出 bug，放最前面。

星枢的 HTTP 服务是**用 ArkTS TCPSocketServer 手写的精简实现**（`ApiServer.ets`），它对每个 TCP 连接只处理**一个请求**然后立刻断开：

```
请求 → 读满 Content-Length 指定的字节 → 路由执行 → 返回响应 → close
```

由此带来 4 条硬约束：

| 约束 | 说明 |
|---|---|
| **每次请求一个新连接** | 响应头永远是 `Connection: close`。**不要开 keep-alive 连接池**，复用连接会拿到空响应或超时 |
| **必须带 `Content-Length`** | 没有 `Transfer-Encoding: chunked` 支持。Body 必须一次发完，长度与头一致，否则服务器会一直等在 `\r\n\r\n` 之后凑够字节 |
| **只解析 `\r\n`** | 换行必须是 CRLF。用标准 HTTP 库（ArkTS `http`、curl、axios）都不成问题；自己拼 socket 报文时注意 |
| **响应编码固定** | `Content-Type: application/json; charset=utf-8`，响应体会被一次性 send 完再关闭 |

另外它自带 CORS 头（`Access-Control-Allow-Origin: *`），所以设备上的 Web 容器页面也能直连：

```
Access-Control-Allow-Origin: *
Access-Control-Allow-Headers: *
Access-Control-Allow-Methods: GET, POST, OPTIONS
```

预检请求 `OPTIONS` 会返回 `{"ok":true}`，且**不需要令牌**。

> 虽然允许 GET，但所有端点都按「路径 + JSON body」工作，**请统一用 POST + JSON**。GET 带 body 在很多客户端库上会被丢掉。

## 3. 开启服务与取令牌

服务不是常开的，要在 App 里手动启动：

1. 打开星枢 → 底栏「接口」页签
2. 点开关启动服务，端口默认 **18790**（可改，建议 1024–65535 且避开已占用端口）
3. 页面会显示当前令牌，形如 `4ce0489d3661f85f68400846`（**24 位十六进制**，首次启动随机生成并持久化）
4. 想换令牌就点重新生成；换完旧令牌立即失效

设置面板（关于页 → 「设置」卡片）里的「本机接口」区也能看到监听地址与令牌。

### 发现端口

不同应用无法约定同一个端口。推荐两种做法：

- **由用户在配置页手填**（最稳）：调用方 App 提供输入框，用户把星枢「接口」页显示的端口和令牌粘进去
- **探测**：对 `127.0.0.1:18790` 优先尝试，失败后再扫 18790–18800 这种小范围；探测时用 `/v1/ping`（免令牌），能拿到 `{"service":"starpivot"}` 就是它

> 不要对 1–65535 全扫。设备上端口扫描会被系统记日志，而且极慢。

## 4. 鉴权

除 `/v1/ping` 和 `OPTIONS` 外，**所有请求都必须带令牌头**：

```http
X-StarPivot-Token: 4ce0489d3661f85f68400846
```

注意几点：

- 头名比较是**大小写不敏感**的（服务器会把头名转小写再比）；传 `x-starpivot-token` 也行
- 旧版本用的是 `X-Starzuku-Token`，当前实现**只认** `X-StarPivot-Token`
- 令牌错了返回 **HTTP 401**，body 为：

```json
{"ok":false,"code":401,"error":"unauthorized: X-StarPivot-Token 不匹配"}
```

- 令牌**没有作用域概念**：拿到令牌就等于拿到全部能力（包括 `/v1/shell`）。所以不要在日志、崩溃上报里打印它
- 令牌只能通过 App 界面查看，没有「程序化获取」的接口——这是有意的

## 5. 通用约定（请求体 / 响应体 / 超时）

### 5.1 请求体

- `Content-Type: application/json`，body 是一个 JSON 对象
- 空 body 也合法（按 `{}` 处理），例如 `/v1/capabilities`
- body 不是合法 JSON → 返回 `{"ok":false,"code":400,"error":"body 不是合法 JSON"}`
- 字段名严格小写，多余字段会被忽略

### 5.2 响应体

所有成功/业务失败的响应都是 200（401 除外），结构分两类：

**A. 命令执行类**（device / shell / tap / swipe / key / file.* / app.*）：

```json
{
  "ok": true,
  "code": 0,
  "out": "命令的 stdout",
  "err": "命令的 stderr（本通道通常为空串）"
}
```

- `ok` = `code === 0`
- `code` 是星枢内部约定的执行状态：`0` 成功，`-1` 通道级失败（连不上 hdcd / 超时 / 缺上下文）
- `out` / `err` 都是**字符串**，可能包含换行、中文、控制字符以外的任意文本

**B. 结构化类**（process/list、screen/capture、ping、capabilities）：字段见各自端点。

### 5.3 超时表

服务器内部各端点的执行超时（不是 HTTP 层超时，客户端应比它更长）：

| 端点 | 服务器超时 | 建议客户端超时 |
|---|---|---|
| `/v1/ping` | 15s（首次要探测 hdcd 端口） | 20s（常驻连接时 <30ms） |
| `/v1/capabilities` | 无执行 | 5s |
| `/v1/device` | 20s | 30s |
| `/v1/shell` | 30s | 40s |
| `/v1/screen/capture` | 单次 30s + base64 60s，最多重试 3 轮 | **90s** |
| `/v1/screen/tap` `/swipe` `/key` | 15s | 25s |
| `/v1/process/list` | 20s | 30s |
| `/v1/process/kill` | 15s | 25s |
| `/v1/file/list` | 30s | 40s |
| `/v1/file/read` | 30s | 40s |
| `/v1/file/write` | 20s | 30s |
| `/v1/file/remove` | 10s | 20s |
| `/v1/app/list` | **90s** | 100s |
| `/v1/app/start` | 20s | 30s |
| `/v1/app/uninstall` | 30s | 40s |

## 6. 端点详解

### /v1/ping

**用途**：探活 + 发现端口。**不需要令牌**。

请求：`POST /v1/ping`，body 可为空。

响应：

```json
{"ok":true,"service":"starpivot","version":"1.1.0","port":18790,"broker":true}
```

| 字段 | 含义 |
|---|---|
| `service` | 固定 `starpivot`，用来识别是不是星枢 |
| `version` | 网关版本号字符串（当前构建里是 `1.1.0`，以 App「关于」页显示为准） |
| `port` | 当前监听端口 |
| `broker` | 通道是否在线（`true` 表示能执行命令） |

**注意**：`ok:true` 只代表 HTTP 服务活着；`broker` 才是「能不能真的执行命令」。如果 `broker:false`，说明 `hdcd` 没连上（本机模式下），此时除 ping 外其它端点都会返回 `code:-1`。

`broker` 为 `false` 时 ping 仍会做一次连接尝试，耗时约 1s；`true` 时如果复用存活连接，耗时 <30ms。

---

### /v1/capabilities

**用途**：问对方支持哪些能力，避免硬编码。

响应：

```json
{
  "ok": true,
  "caps": [
    "device", "shell",
    "screen.capture", "screen.tap", "screen.swipe", "screen.key",
    "process.list", "process.kill",
    "file.list", "file.read", "file.write", "file.remove",
    "app.uninstall", "app.start", "app.list"
  ]
}
```

调用方应把它当作**能力声明**，不存在的能力自己降级。注意这里没有 `app.install`：安装 HAP 不在接口里。

---

### /v1/device

**用途**：设备基本信息。

响应 `out` 是**多行 key=value 文本**（不是 JSON）：

```json
{"ok":true,"code":0,
 "out":"model=SLG-W50\nbrand=HUAWEI\napi=26\nver=HarmonyOS 6.x.x\n",
 "err":""}
```

解析建议：按行 `split('\n')`，每行 `split('=', 2)`，容忍空行与 `errNum 106` 这类失败残留。

**已知限制**：`uid=2000` 下 `param get` 某些键会失败（尤其序列号 `const.product.sn`），此时那一行会变成 `model=errNum 106 ...` 之类的文本。序列号请改用其它途径（例如用户在 App 内「关于」页看到的值），别把它当作调用方必需字段。

---

### /v1/shell

**用途**：逃逸口。执行任意一条 shell 命令。

请求：

```json
{"cmd": "ls -l /data/local/tmp"}
```

响应：命令执行类结构，`out` 是 stdout，`err` 通常为空串（stderr 会混进 out，取决于命令是否自行重定向）。

**规则与坑**：

- `cmd` 不能为空，空则返回 `{"ok":false,"error":"缺少 cmd"}`
- 服务器执行 `30s` 超时；超时返回 `code:-1`
- **不要指望它处理超大输出**。这条路径不带结束哨兵，靠内部空闲窗口判定命令结束：输出几百 KB 时可能被截断，或多等 2.5 秒。大输出请用 `/v1/file/read`、`/v1/app/list` 这类自带哨兵的端点
- 命令里如果有交互等待（例如 `vim`、需要输入的 `read`），会一直挂到 30s 超时
- 想拿退出码？带上 `echo $?`，自己从 out 尾部解析
- 命令会以 `uid=2000(shell)` 执行，`$HOME` 是 `/`，`PATH` 是系统默认

---

### /v1/screen/capture

**用途**：截屏，返回 JPEG 的 base64。

请求：

```json
{"width": 1600, "height": 0}
```

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `width` | number | `1600` | 目标宽度 px。`0` 或负数 = 屏幕原生宽度（实测 2800） |
| `height` | number | `0` | 目标高度 px。`0` = 按屏幕真实比例自动算；>0 = 强制该高度（最低 400） |

响应：

```json
{"ok":true,"mime":"image/jpeg","base64":"/9j/4AAQSkZJRgABAQ..."}
```

失败（重试 3 轮仍失败）：

```json
{"ok":false,"error":"截屏失败"}
```

**分辨率语义（重要）**：底层的 `snapshot_display` 的 `-w` 与 `-h` 是**各自独立生效**的。只传 `-w 1600` 会让高度保持 1840，画面被横向压扁成 1:1.15。星枢已经处理了这件事：不传 `height` 时用 `getDefaultDisplaySync()` 的宽高算出 `h = round(w * 真实高 / 真实宽)`，然后把 `-w -h` 一起传下去。**你自己算比例时不要重复压扁**。

**耗时量级（2800×1840 设备实测）**：

| 分辨率 | 生成 JPEG | base64 编码 | 合计设备侧 | App 侧取回 + base64 传输 |
|---|---|---|---|---|
| 2800×1840 | ≈494ms | ≈74ms | ≈0.6s | 最慢，约 1.5–3s |
| 1600×1051 | ≈200ms | ≈30ms | ≈0.3s | ≈0.8–1.5s |
| 1080×710 | ≈120ms | ≈20ms | ≈0.2s | ≈0.5–1s |

建议：**需要展示就用 1600 或 1200；只有 OCR / 细节识别才用原生分辨率。** 原生分辨率下单次响应体约 300–500 KB base64，字符串解析也吃内存。

**可靠性机制**（你不用关心，但知道能帮助你判断"是不是没截到"）：

1. 先 `stat -c %s` 拿文件真实字节数
2. 计算期望 base64 长度 `ceil(size/3)*4`
3. 严格比对长度，不符视为传输截断 → 重试（最多 3 轮）

所以拿到 `ok:true` 时图像一定是完整的；`ok:false` 说明设备侧 `snapshot_display` 本身失败了（常见于息屏、或被系统限制）。

**常见失败原因**：屏幕处于息屏/锁屏、当前前台应用禁截（安全界面）、`/data/local/tmp` 写满、`snapshot_display` 被系统限流。

### /v1/screen/tap

**用途**：点击一个坐标。

请求：

```json
{"x": 1400, "y": 900}
```

响应：命令执行类。底层是 `uitest uiInput click <x> <y>`。

**坐标系**：**物理像素**（不是 vp/dp），原点左上。2800×1840 的设备上 x∈[0,2800]、y∈[0,1840]。调用方如果只知道自己界面的 vp 坐标，需要自己乘 `display.densityPixels`。

`x`/`y` 缺省值时按 `0` 处理——**别漏传**，否则会点左上角。

---

### /v1/screen/swipe

**用途**：滑动。

请求：

```json
{"x1": 1400, "y1": 1400, "x2": 1400, "y2": 400, "duration": 300}
```

| 字段 | 默认 | 说明 |
|---|---|---|
| `x1,y1,x2,y2` | `0` | 起止点，物理像素 |
| `duration` | `300` | 期望时长（毫秒） |

实现细节：`uitest uiInput swipe` 的第 5 个参数是**速度**（px/s，允许 200–40000），星枢把 `duration` 换算成速度：`v = round(distance / (duration/1000))`，并 clamp 到 [200, 40000]。所以 `duration` 只是近似——给 200ms 以下的极短时长会被速度下限拉长。

---

### /v1/screen/key

**用途**：注入按键事件。

请求：

```json
{"key": "Back"}
```

`key` 缺省 `Back`。取值就是 `uitest uiInput keyEvent` 支持的键名，常用：`Back`、`Home`、`Power`、`VolumeUp`、`VolumeDown`、`Enter`。

响应：命令执行类。

### /v1/process/list

**用途**：进程列表。**已结构化**，不需要自己解析 `ps -ef`。

请求：空 body。

响应：

```json
{
  "ok": true,
  "count": 187,
  "items": [
    {"uid": "root", "pid": 1, "name": "/init"},
    {"uid": "u:r:shell:s0", "pid": 19497, "name": "hdcd"},
    {"uid": "u:0_a1", "pid": 21061, "name": "com.starpivot.xs"}
  ]
}
```

| 字段 | 说明 |
|---|---|
| `uid` | `ps -ef` 第一列原样（可能是 `root` 或 `u:r:xxx:s0` 这类 SELinux 标签） |
| `pid` | 数字 |
| `name` | 最后一列（可执行路径或进程名） |

失败时返回命令执行类结构（`ok:false` + `code` + `out`/`err`），此时 `items` 不存在——调用方先判 `ok` 再取 `items`。

解析规则：按空白切列，第一列 uid、第二列 pid、最后一列 name；pid 非数字的行被丢弃。

---

### /v1/process/kill

**用途**：结束进程。

请求：

```json
{"pid": 21061}
```

底层执行 `kill -9 <pid>`。响应：命令执行类。

**注意**：

- `kill -9` 是硬杀，没有优雅退出
- 杀系统关键进程（`hdcd`、`init`、当前前台应用）可能让你自己的通道断掉。**不要杀 `hdcd`**（实测被 SELinux 拒绝，且会直接毁掉通道）
- 杀 `com.starpivot.xs` 自己 = 自杀

---

### /v1/file/list

**用途**：列目录。返回 `ls -lA` 的**原始文本**（未结构化）。

请求：

```json
{"path": "/data/local/tmp"}
```

`path` 缺省 `/data/local/tmp`。

响应 `out` 示例：

```
total 24
-rw------- 1 shell shell 134963 2026-11-15 10:22 .sp_shot.jpeg
drwxrwxrwx 2 shell shell   4096 2026-11-14 09:10 sub
drwxr-xr-x 2 root root    4096 2026-11-13 08:00 other
```

解析建议（按列数容错，别假设固定列宽）：

```
列0    权限串（d 开头是目录，l 开头是链接）
列1    硬链接数
列2    属主
列3    属组
列4    字节数（目录也是数字）
列5    月
列6    日
列7    时/年
列8+   名字（可能含空格，必要时用 ls -lA 的原始行截取）
```

**坑（这也是 XS 管理器踩过的）**：

- `total N` 那行要跳过
- 第一列不是权限串的行（空行、错误残留如 `ls: /xxx: Permission denied`）要跳过，并且**区分「空目录」与「请求失败」**
- 大目录（几千项）输出可达上百 KB。本端点带结束哨兵，不截断，但客户端要允许 40s 超时
- `A` 会包含 `.` 开头的隐藏项

---

### /v1/file/read

**用途**：读文件文本。

请求：

```json
{"path": "/data/local/tmp/x.json"}
```

底层是 `cat "<path>" 2>&1`，带结束哨兵（大文件不截断，超时 40s）。

响应 `out` 即文件全文。**只适合文本**：二进制（jpeg/png/so/hap）读出来是乱码，请用截屏接口或自己走 shell + base64。

建议：读之前先用 `/v1/file/list` 或本地判断按后缀区分文本/二进制。

---

### /v1/file/write

**用途**：把字符串写入文件（覆盖）。

请求：

```json
{"path": "/data/local/tmp/a.txt", "content": "hello\n世界"}
```

实现：`printf '%s' '<content>' > "<path>"`，其中 `content` 里的单个单引号会被转义成 `'\''`（已验证可安全传入）。响应：命令执行类。

**限制**：

- 只写**文本**，没有 base64 写二进制接口（内部 `pushBase64` 只给截屏/安装用，未暴露）
- **不加末尾换行**：写什么就是什么，想留尾换行要自己在 `content` 里带 `\n`
- 覆盖语义，不是追加；不会自动建父目录
- 超大内容（几 MB）会受命令长度与 20s 超时限制，不建议超过几百 KB
- 路径里含双引号会破坏命令拼接，避免

---

### /v1/file/remove

**用途**：删除文件。底层 `rm -f "<path>"`。

请求：

```json
{"path": "/data/local/tmp/a.txt"}
```

响应：命令执行类。注意 `rm -f` **不报错**：文件本来不存在也返回 `code:0`。删不掉（权限/SELinux）时 out 里会有 `Permission denied` / `Operation not permitted`，但 `code` 仍是 0——**要判断成功得看 out 是否为空**。

`rm -f` 不带 `-r`，**删目录会失败**。

---

### /v1/app/list

**用途**：已安装应用列表。底层 `bm dump -a -l`，**原始文本**。

请求：空 body。响应：命令执行类，超时 90s（装几百个应用的机器输出可到几百 KB，本端点带结束哨兵不会截断）。

`out` 形如：

```
ID: 100
    bundleName: com.starpivot.xs
    label: 星枢
ID: 200
    bundleName: com.starfiles.xs
    label: XS管理器
```

解析建议：按行匹配 `bundleName:` 与 `label:`，两者配对成一个应用；`ID:` 行可跳过。注意 label 可能是多语言资源解析后的中文名。

> 这是**唯一能拿到应用中文名**的端点，比逐个 `bm dump -n <bundle>` 快得多。

---

### /v1/app/start

**用途**：启动应用。

请求：

```json
{"bundle": "com.starfiles.xs"}
```

底层：`aa start -a EntryAbility -b "<bundle>" || aa start -b "<bundle>"`（先试标准入口名，失败回退不指定 ability）。响应：命令执行类。

**注意**：

- 需要目标应用有可启动的入口 ability；纯后台 service 应用会失败
- 输出里出现 `error: failed to start ability` 就是没起来
- 若目标应用被系统冻结/未安装，同样失败

---

### /v1/app/uninstall

**用途**：卸载应用。

请求：

```json
{"bundle": "com.example.xsui"}
```

底层 `bm uninstall -n "<bundle>"`，超时 30s。响应：命令执行类。成功时 out 里通常有 `uninstall bundle successfully`。

**注意**：`bm uninstall` 对系统应用、以及正在运行的应用可能失败；卸载星枢自己会让服务立即中断。

## 7. 错误码与失败语义

### HTTP 层

| HTTP | 场景 | body |
|---|---|---|
| 200 | 一切正常，以及业务失败 | JSON（见下） |
| 401 | 令牌缺失或不匹配 | `{"ok":false,"code":401,...}` |
| 500 | 路由内部异常（极少见） | `{"ok":false,"error":"internal error"}` |

### 业务层 `code`

| code | 含义 | 典型原因 | 调用方该做什么 |
|---|---|---|---|
| `0` | 成功 | — | 正常处理 `out` |
| `-1` | 通道级失败 | hdcd 没连上 / 端口探测失败 / 命令超时 / 缺 Ability 上下文 | 重试一次；仍失败就提示用户去 App 点「启动」或切到「仅本机」 |
| 其它正数 | 命令退出码 | 命令本身失败（`ls` 找不到路径等） | 看 `out`/`err` 内容判断 |
| `400` | body 不是合法 JSON | 拼错引号、没序列化 | 修请求 |
| `401` | 令牌错 | 头名写错 / 令牌过期 | 重新取令牌 |
| 无 `code` 但有 `error` | 参数缺失 | `cmd` 为空、`path` 为空 | 补参数 |

### 特别提醒

`/v1/shell` 与 `/v1/file/remove` 存在「`code:0` 但实际失败」的情况（shell 不返回退出码；`rm -f` 静默）。**判断成败不能只看 `ok`**，要看 `out` 里是否含错误关键词（`Permission denied`、`No such file`、`error:`）。

## 8. 调用示例

### 8.1 curl

```bash
TOKEN=4ce0489d3661f85f68400846
BASE=http://127.0.0.1:18790

# 探活（免令牌）
curl -s -X POST $BASE/v1/ping

# 能力
curl -s -X POST $BASE/v1/capabilities -H "X-StarPivot-Token: $TOKEN"

# 设备信息
curl -s -X POST $BASE/v1/device -H "X-StarPivot-Token: $TOKEN"

# 截屏并落盘
curl -s -X POST $BASE/v1/screen/capture \
  -H "X-StarPivot-Token: $TOKEN" -H "Content-Type: application/json" \
  -d '{"width":1600}' \
  | python -c "import sys,json,base64;d=json.load(sys.stdin);open('shot.jpg','wb').write(base64.b64decode(d['base64']))"

# 目录
curl -s -X POST $BASE/v1/file/list -H "X-StarPivot-Token: $TOKEN" \
  -H "Content-Type: application/json" -d '{"path":"/data/local/tmp"}'

# shell
curl -s -X POST $BASE/v1/shell -H "X-StarPivot-Token: $TOKEN" \
  -H "Content-Type: application/json" -d '{"cmd":"id; echo __RC=$?"}'
```

> 注意：因为服务只监听设备自己的 `127.0.0.1`，**电脑上的 curl 连不到**。想在电脑上测，先建立端口转发：
> `hdc fport tcp:18790 tcp:18790`，然后查 `hdc fport ls` 拿设备侧端口。

### 8.2 ArkTS（调用方应用里）

```ts
import { http } from '@kit.NetworkKit';

interface CaptureResp {
  ok: boolean;
  mime?: string;
  base64?: string;
  error?: string;
}

async function capture(base: string, token: string): Promise<string> {
  const req = http.createHttp();
  try {
    const resp = await req.request(base + '/v1/screen/capture', {
      method: http.RequestMethod.POST,
      header: { 'Content-Type': 'application/json', 'X-StarPivot-Token': token },
      extraData: JSON.stringify({ width: 1600 }),
      connectTimeout: 3000,
      readTimeout: 90000          // 截屏必须给足
    });
    if (resp.responseCode !== 200) return '';
    const obj = JSON.parse(resp.result as string) as CaptureResp;
    return obj.ok && obj.base64 ? obj.base64 : '';
  } catch (e) {
    return '';
  } finally {
    req.destroy();                // 每次新建，必须 destroy
  }
}
```

要点：

- **每个请求新建 `http.createHttp()`，用完 `destroy()`**。服务端不复用连接，客户端也别复用
- `readTimeout` 按第 5.3 节表来，截屏/应用列表尤其要给足
- 不要并发打同一个端点（见第 9 节）

## 9. 并发、超时与限流

星枢内部把**所有请求串行化**：「接口」层有一个队列，同一时刻只跑一个命令。原因是底层 `hdcd` 会话只有一条，并发会让回包错位甚至卡死整条通道（这是实测过的故障，根因是全局接收缓冲被后一次连接重置，导致前一条在途回包被冲掉）。

对你的影响：

| 现象 | 原因 | 怎么做 |
|---|---|---|
| 第 2 个请求等很久才返回 | 排队到第 1 个（可能是 30s 的命令）后面 | 自己的客户端也做串行队列，别并发刷 |
| 两个页面同时刷新，全部超时 | 队列堆积 + 客户端超时太短 | 刷新去抖动 + 分页/增量 |
| 一个大目录列表把整个 App 卡住 | `/v1/file/list` 排在最前，后面全堵 | 大目录用分页或 `/v1/shell` 自取局部 |

**推荐调用方策略**（来自一次真实故障的复盘）：

1. **串行队列**：自己维护一条 Promise 链，所有调用走它（等同 `ApiServer.queue` 的做法）
2. **刷新去抖动**：滚动/输入触发刷新时 200–300ms 合并一次
3. **超时 8–10s + 只重试一次**：对 `/v1/file/list` 这类，别设 30s 然后重试三次，会把队列拖死
4. **低频心跳**：`/v1/ping` 5–10s 一次足够，别 1s 一次（每次 ping 都可能触发一次探测）
5. **优先结构化端点**：能用 `/v1/file/list` 就别用 `/v1/shell "ls -lA ..."` 自己拼

## 10. 截图性能与分辨率

已经在本版本的截屏路径上做过一轮专项优化，理解这些参数能帮你选对档位：

- 设备侧 `snapshot_display -f` 写 2800×1840 的 JPEG 约 **494ms**（232 KB），`base64 -w 0` 约 **74ms** → 设备侧合计 <0.6s
- 慢的是「取回」：整段 base64 要经 socket 分帧回传。所以**分辨率直接决定往返时间**
- 本版本用「哨兵 + 长度校验」取代了「空等 2.5 秒猜结束」：先 `stat` 拿字节数，期望长度 `ceil(size/3)*4`，不符即重试。因此不会出现「图看着回来了但其实是半张」

选档建议：

| 用途 | width | height | 预期耗时 |
|---|---|---|---|
| 缩略图 / 状态回显 | 800–1200 | 0（按比例） | 0.5–1s |
| 界面截图分享 | 1600 | 0 | 0.8–1.5s |
| OCR / 细节识别 | 0（原生 2800） | 0 | 1.5–3s |

自定义不成比例的画幅（例如 `{"width":1200,"height":900}`）会**拉伸画面**，因为底层就是把原图按给定宽高重采样。想要不变形就传 `height:0`。

## 11. 安全边界

- 只监听 `127.0.0.1`，局域网内的其它设备连不进来
- 令牌 24 位十六进制、随机生成、持久化在应用私有 prefs（`starpivot` 库）
- 拿到令牌 = 拿到 `uid=2000` 的全部能力。**不要在第三方日志/崩溃上报里记录令牌**
- 不要把这套接口暴露给不可信的应用或 Web 页面：CORS 是 `*`，任何本地页面都能调
- 星枢不提供「安装 HAP」和「改签名」接口，这是刻意的设计取舍

## 12. 排查表

| 现象 | 最可能的原因 | 处理 |
|---|---|---|
| 连接被立即关闭 / 拿不到响应 | 客户端用了 keep-alive 复用连接 | 每请求新建连接 |
| 请求一直挂着不回 | 没带 `Content-Length`，或 body 长度与头不一致 | 用标准 HTTP 库，别手拼 |
| 401 | 头名写成 `X-Starzuku-Token`，或令牌已重新生成 | 用 `X-StarPivot-Token`，重新取令牌 |
| `{"ok":false,"error":"unknown endpoint"}` | 路径拼错（注意末尾斜杠也不行） | 严格用 `/v1/xxx` |
| 所有端点 `code:-1` | `hdcd` 没连上（App 概览页显示未连接） | 让用户在 App 点「启动」；或切「仅本机」重试 |
| 截屏 `ok:false` | 息屏/锁屏、前台是安全界面 | 唤醒解锁后重试 |
| 截屏图被压扁 | 调用方自己传了不成比例的 `width/height` | `height` 传 0 |
| 列表返回空 | 目录真的空，或 `ls` 报权限错误 | 看 `out` 是否含 `Permission denied` |
| `rm` 返回 ok 但文件还在 | `rm -f` 静默 + 权限/SELinux 拒绝 | 检查 `out` 是否非空 |
| 命令全排队、越来越慢 | 并发调用 + 长命令堆积 | 客户端串行 + 去抖动 |
| 无法通过电脑 curl 访问 | 服务只绑回环 | `hdc fport tcp:18790 tcp:18790` |
